收到一份外部审计报告后，我用 anon key 对线上 Supabase 做了**实测复核**，逐条核对：

| 报告结论 | 实测结果 | 判定 |
|---------|---------|------|
| 数据库大门敞开，可增删改查全部成功、可删除全部打卡记录 | 删除打卡记录被拒绝：`"Data is immutable"`（触发器生效）；删除 config 行返回 0 行（无删除策略）。**说明 RLS 已生效，删除已被封堵** | 报告过时（应为启用 RLS 前的结论） |
| 可插入任意打卡记录 | **属实且严重**：插入 `date=2020-01-01` 的越界打卡竟返回 201 成功。说明 punches 表存在遗留的宽松 INSERT 策略，与严格策略 OR 叠加，绕过了 7 天范围校验 | **确认漏洞，已给出修复 SQL** |
| 管理员密码写在源码、客户端验证 | 属实，架构固有（见下方风险 1） | 属实 |
| 员工密码哈希可公开读到 | 属实，架构固有（见下方风险 2） | 属实 |
| 缺 CSP / HSTS / X-Frame-Options，CORS 为 `*` | CSP 已有（meta 标签）；但 **HSTS、X-Frame-Options、CSP 响应头确实缺失**；Supabase API 的 CORS 确实会反射任意来源 | 部分属实，已补 `_headers` |

### 本次据此新增的两项修复

**A. punches 越界插入漏洞（高危，需在 Supabase 执行 SQL）**
- 实测确认：越界日期打卡可写入，7 天范围校验被遗留策略绕过
- 修复脚本 `supabase-rls-修复v2.sql`：用 `DO` 块**动态删除四张表上的所有现存策略**（含手动/默认宽松策略），再重建严格策略集，并 `FORCE ROW LEVEL SECURITY`；同时清理本次检测遗留的 `__SECTEST__` 测试行
- ⚠️ 需你在 Supabase → SQL Editor 执行该脚本才生效；执行后可再次尝试越界插入验证会被拒绝

**B. HTTP 安全响应头缺失（中危，已随部署包补齐）**
- 新增 Cloudflare Pages `_headers` 文件，为全站补上：HSTS（强制 HTTPS、防降级）、X-Frame-Options: DENY（防点击劫持）、CSP 响应头（含 `object-src 'none'`、`base-uri 'self'`、`form-action 'self'`）、Permissions-Policy（禁用摄像头/麦克风/定位等）、COOP/CORP
- 已打进 `clockin-deploy.zip`，重新部署即生效

## 二、仍存在的风险（按严重度排序）

### 严重（需架构改造才能解决）

**1. 客户端管理员身份可伪造**
- 管理权限完全靠 localStorage 中的 `cs6`（过期时间）和 `cs6tk`（token）判断
- 任何人打开浏览器 DevTools 执行两行代码就能获得"管理员"身份：
  ```javascript
  localStorage.setItem('cs6', String(Date.now() + 604800000));
  localStorage.setItem('cs6tk', 'fake.' + btoa(navigator.userAgent).slice(0,16));
  ```
- **影响：** 可以访问管理后台 UI，看到所有日志、成员数据、选班情况
- **修复方向：** 引入 Supabase Auth，管理员身份在服务端验证

**2. 员工密码哈希随 TEAM 数据下发给所有客户端**
- config 表的 team 行包含所有员工的 `pwd` 字段（SHA-256 哈希）
- 任何人访问网站后都能在 DevTools 里看到所有人的密码哈希
- 默认密码 `123456` 的哈希值公开可查（彩虹表秒破）
- **影响：** 员工密码泄露
- **修复方向：** 密码验证改为 Supabase Edge Function（服务端），客户端永远拿不到哈希

### 高（客户端架构固有限制）

**3. API Key 暴露 + config 表可写**
- Supabase anon key 在前端源码中，配合 RLS 策略，任何拿到 key 的人可以：
  - 读取全部数据（config/punches/claims/logs）
  - 覆写 config 表中的 team/picks/selcfg 数据（RLS 允许写入）
  - 插入 7 天内的打卡记录
  - 插入任意操作日志
- **已有的保护：** RLS 禁止删除 config 行、禁止修改/删除打卡记录和日志、打卡日期限 7 天
- **修复方向：** 更换为 service_role key 放服务端，前端改用 Supabase Auth 的 access_token

**4. 客户端时钟可篡改打卡时间（本轮已缓解）**
- ~~打卡时间取自 `new Date()`，修改系统时钟可以伪造打卡时间~~
- 已改为服务器时间锚定：打卡时实时从 Supabase 响应头获取服务器时间，本地时钟被篡改也不影响记录时间；仅在完全离线时回退本地时间
- **残留风险：** 完全离线场景仍用本地时间；彻底解决需服务端打卡（Edge Function 写入服务器时间戳）

**5. localStorage 全量可篡改**
- 所有状态（选班/规则/绑定/暴力破解锁）存在 localStorage
- 通过 DevTools 可以：绕过选班锁定、跳过人数上限、清除暴力破解锁定、伪造员工绑定
- **影响：** 仅限本机（自己的浏览器），不影响其他人的数据
- **修复方向：** 关键业务规则在服务端强制执行

### 中（可改善但非紧急）

**6. 设备指纹不够唯一**
- `devFp()` 使用 UA + 屏幕 + 时区 + 语言 + CPU 核心数等，很多设备值完全相同
- 同一型号电脑 + 同一浏览器的用户，指纹可能一致
- **影响：** 设备绑定可能被同型号设备绕过
- **修复方向：** 绑定改为 Supabase Auth session（设备无关）

**7. 全员数据互相可见**
- 选班情况计数表对全员公开（设计如此），所有人能看到所有人的选班数
- 员工姓名、部门对所有登录用户可见
- **影响：** 隐私暴露，但属于业务需求（公开计数表）

**8. SSRF 过滤不完整（本轮已修复）**
- ~~同步链接拦截了 localhost/127.0.0.1/192.168.x/10.x，但遗漏了 172.16-31.x、0.0.0.0、IPv6（::1）、云元数据（169.254.169.254）~~
- 已升级为 `isPrivateHost()` 全覆盖拦截，保存和定时拉取两处都校验，见"已修复"表 #5

**9. CSP 允许 unsafe-inline 和 unsafe-eval**
- 因为系统大量使用 `onclick` 等内联事件处理器，CSP 不得不放行
- 削弱了 XSS 防护效果
- **修复方向：** 重构为 React/Vue 等框架后可移除

## 三、风险评估总结

| 等级 | 数量 | 说明 |
|------|------|------|
| 严重 | 2 | 客户端管理员伪造 + 密码哈希泄露（均需架构改造） |
| 高 | 2 | API Key 暴露 + localStorage 篡改（客户端固有限制） |
| 中 | 3 | 指纹不唯一 + 数据互可见 + CSP 宽松 |
| 已修复 | 8 | XSS + 密码提示移除 + 入口隐藏 + 连接测试 + SSRF 全覆盖 + 时钟锚定 + punches 越界插入(需执行SQL) + 安全响应头(需重新部署) |

### 核心结论

当前系统的 4 个严重/高级风险都源于同一个根本问题：**单文件前端架构无法实现真正的权限控制**。所有鉴权、业务规则、数据验证都在客户端执行，而客户端代码对用户完全透明。

这些风险在**内部小团队使用场景下是可接受的**（15人左右的团队，彼此认识，不太可能有恶意攻击者），但如果要面向更大规模或公开部署，建议进行以下架构升级：

1. **引入 Supabase Auth** — 管理员和员工都通过 Auth 登录，session 由服务端管理
2. **密码验证改为 Edge Function** — 客户端不接触密码哈希
3. **关键业务规则服务端化** — 选班上限、打卡时间验证在 Edge Function 中执行
4. **RLS 策略收紧** — 用 `auth.uid()` 替代 `true`，实现行级权限控制
