# 考勤打卡系统 — 系统优化与风险分析报告

> 分析对象：`index.html`（单文件应用，4886 行 / ~364KB，版本 v2026.08.05.15）+ Supabase 后端 + `outputs/` 历史文档与 SQL
> 分析方式：纯只读代码考古（Grep 定位 + 精读关键模块），交叉验证 `outputs/安全测试报告.md`、`outputs/安全风险排查报告.md`、`outputs/优化备忘录.md`、`outputs/supabase-*.sql`、`outputs/_headers`、`test_outputs/run_regression*.log`
> 分析视角：A 产品经理 / B 全栈开发工程师 / C 安全·合规·运营·业务风险专家
> 严重度定义：**P0** = 立即处理（资损/数据失真/可被利用的安全漏洞）；**P1** = 尽快处理（明显缺陷或高风险隐患）；**P2** = 计划处理（体验/架构/长期债务）
> 工作量定义：小 = ≤1 人日；中 = 2~5 人日；大 = >1 人周

---

## 0. 执行摘要（关键结论）

1. **历史报告宣称的修复大部分属实**：服务端化 picks（advisory lock + 每日上限 7）、punches/logs 不可变触发器、FORCE RLS、服务器时间锚定、暴力破解锁定、CSP meta、输入 sanitize 均已在代码/SQL 中得到验证。
2. **但发现三处"宣称已修复/已防护、实际未落地"的重大落差**：
   - `outputs/_headers` 实际只有 2 条缓存规则（122 字节），**完全没有**《安全风险排查报告》宣称已添加并验证的 HSTS / X-Frame-Options / CSP 响应头 / Permissions-Policy（所有部署 zip 中同样是这份残缺文件）；
   - `hmacSign/hmacVerify` 完整性签名**是死代码**——定义了但没有任何写入路径调用它，"数据完整性签名"实际不提供任何保护；
   - `adminClearAll` 的服务端删除被 RLS/触发器静默拦截，"清空"只清了本地，**服务端数据原封不动**，造成前后端数据永久分叉。
3. **两个历史报告已确认但未解决的 P0 仍然存在**：管理员认证完全在客户端（可伪造）、TEAM 密码哈希通过 config 表对所有人暴露。
4. **工程质量警报**：无 git 版本库（只有手工 .bak）、回归测试套件当前失败（`run_regression6.log` 中 login_admin 超时）、364KB 单文件无模块化。
5. **业务证据链缺陷**：补卡/请假审批人硬编码为 `'管理员'`，离线打卡回退本地时钟，作为劳动仲裁证据时证明力不足。

## A. 产品经理视角

### A-1 审批流程单点依赖，无代理/超时机制 【P1｜工作量：中】
- **证据**：补卡审批 `acceptMakeup`/`rejectMakeup`（L2872-2911）、请假审批 `approveLeave`/`rejectLeave`（L3191-3207）、换班审批均只有唯一的"管理员"入口；代码中不存在代理审批人、审批超时提醒、待办数量提示或催办机制。
- **问题**：管理员休假/离职时，补卡、请假、换班申请无限积压；月底绩效结算（`calcMonthMetrics` L3307-3379 依赖已审批数据）会被阻塞。
- **建议**：① 增加"代理管理员"角色（至少 2 人可审批）；② 申请超过 48h 未处理时在管理面板红色标记 + 版本横幅提醒；③ 审批动作记录时间戳用于 SLA 统计。

### A-2 审批人不具名，员工侧信息不对称 【P1｜工作量：小】
- **证据**：`m.decidedBy='管理员'`（L2902、L2911）、`l.decidedBy='管理员'`（L3199、L3207）——四处硬编码，无法区分是哪位管理员做的决定。
- **问题**：员工看到"被拒绝"却不知道找谁申诉；多管理员场景下无法追责；审批理由 `rejectReason` 虽有字段但员工端缺少主动通知（依赖轮询/Realtime 被动同步，错过即不知情）。
- **建议**：`decidedBy` 记录登录管理员的真实姓名/ID；申请状态变更时写入通知队列，员工端顶部显示未读红点。

### A-3 离线打卡体验与规则不闭环 【P1｜工作量：中】
- **证据**：`doPunch`（L1951-2021）正常路径使用服务器时间锚定（L1956），但**离线时回退本地时钟**直接打卡；`validatePunch`（L761-775）允许"7 天前 ~ 明天"的宽窗口。
- **问题**：① 离线打卡无"待复核"状态，与正常打卡混在一起，员工不知道这条打卡是否可信；② 7 天补录窗口过大，产品上形同"事后随意补打卡"，削弱考勤严肃性；③ 无离线打卡的明确提示文案与后续处理流程。
- **建议**：① 离线打卡标记 `offline=true` 并进入"待管理员确认"状态；② 补录窗口收窄到 48h，超过必须走正式补卡申请；③ 打卡成功页显示"使用服务器时间/本地时间"来源。

### A-4 设备与时区边界场景缺失 【P2｜工作量：中】
- **证据**：设备指纹 `devFp()` v2（L826-836）仅由 `screen.width/height`、时区、CPU 核数、colorDepth 拼成；跨天班次（shift 23 = 23:00-00:00，24/25 = 00:00-02:00）存在，`validatePunch` 允许 tomorrow。
- **问题**：① 员工换手机/换浏览器时指纹变化，但没有"换设备申诉/重新绑定"流程，可能直接被拦或静默放行（策略不一致）；② 跨天班次的打卡归属日期（23:59 打 vs 00:01 打）缺少产品规则说明；③ 跨时区出差场景完全未考虑（全部按本地时区解释）。
- **建议**：① 指纹不匹配时给出"申请换设备"入口而非硬拦截；② 跨天班次明确"按班次开始日期归属"并在 UI 标注；③ 记录打卡时区偏移量（`getTimezoneOffset`）入库。

### A-5 绩效数据对员工不透明 【P2｜工作量：小】
- **证据**：`calcMonthMetrics`（L3307-3379）由 picks/punches/leaves/makeups 自动计算迟到/缺卡/工时。
- **问题**：员工只能看到结果数字，看不到"为什么"——哪条打卡导致迟到判定、容差是多少分钟（5 分钟容差硬编码），月末争议只能线下吵。
- **建议**：绩效详情页展示每条判定的依据（对应打卡记录 + 规则文案），并提供"对判定有异议 → 发起补卡申请"的直达入口。

### A-6 建议建立的度量指标 【P2｜工作量：小】
- 打卡一次成功率、离线打卡占比、审批平均时长（提交→决定）、补卡申请率（补卡数/总打卡数，>5% 说明流程或规则有问题）、换班撮合成功率、月末绩效争议数、版本升级后的报错率（`99_*_error.png` 截图显示历史上多次流程回归失败）。

## B. 开发工程师视角

### B-1 364KB 单文件架构，维护性已达极限 【P1｜工作量：大】
- **证据**：全部 HTML/CSS/JS 集中在 `index.html`（4886 行），安全模块、数据层、UI、业务逻辑全部内联；无模块系统、无构建、无类型检查。
- **问题**：任何改动都要在 4886 行里人肉搜索定位；函数间通过全局变量耦合（`TEAM`、`shifts`、`selCfg` 等）；无法做单元测试隔离；历史上多轮"优化"只能叠加补丁（`优化备忘录.md` 记录了 3 轮优化 + 5 项技术债仍在）。
- **建议**：分阶段拆分——阶段 1（中）：按 `<script>` 块拆为独立 .js 文件 + Vite 打包，不改逻辑；阶段 2（大）：数据层（Supabase/localStorage 双写）抽为独立 service 层并补单测；阶段 3：UI 组件化。

### B-2 无 git 版本控制 【P1｜工作量：小】
- **证据**：项目根目录无 `.git`；版本管理依赖手工 `.bak` 文件与文件名版本号（`APP_VERSION='v2026.08.05.15'` L4821）。
- **问题**：无法 diff/回滚/追责改动；多人协作不可能；`_headers` 这类"修复丢失"事故（见 C-5）在 git 下本可被 review 拦截。
- **建议**：立即 `git init` + 首次提交 + 推送私有远端；把 `test_scripts/` 回归测试接入 CI（push 触发）。

### B-3 localStorage + Supabase 双写一致性是最大架构隐患 【P0｜工作量：大】
- **证据**：① `syncToFB`（L1169 附近）每次变更**全量 upsert 整个 shifts + TEAM 数组**到 config 表，冲突策略为 last-write-wins，无版本号/向量时钟；② 本地键 `cp6/cv6/ct6/csc6/cswap6/cmkup6/cleave6/cperf6` 与 Supabase 表互为镜像；③ `initFBListeners`（L1262-1377）Realtime + 自适应轮询拉远端覆盖本地。
- **问题**：两个管理员同时改排班 → 后写覆盖先写，**无任何冲突提示**；网络分区期间本地写入会在恢复后被远端快照静默覆盖，用户数据"凭空消失"且无日志；全量 upsert 随团队规模线性膨胀（每次写全表数据含密码哈希，见 C-3）。
- **建议**：短期（中）：给每条记录加 `updated_at` + 客户端写入前比较，冲突时提示人工合并；长期（大）：排班/申请类数据全部迁移到服务端 RPC 修改（picks 表已示范了正确做法：`pick_set/pick_add/pick_add_cap` + advisory lock，见 `supabase-服务端化picks表.sql`），客户端只做读与提交意图。

### B-4 HMAC 完整性签名是死代码 【P1｜工作量：小】
- **证据**：`hmacSign/hmacVerify`（安全模块 L601-791 区间内）已定义，且 `hmacVerify` 在无签名时直接 `return true`（L639，兼容旧数据）；全文件搜索**没有任何写入路径调用** `hmacSign`。
- **问题**：安全报告宣称的"数据完整性签名防护"实际为零；同时死代码给后续维护者错误的安全感。
- **建议**：二选一：① 在补卡/请假/打卡写入路径真正接入签名并在服务端校验（中）；② 删除死代码并在文档中如实标注"完整性依赖 Supabase RLS + 不可变触发器"（小）。

### B-5 adminClearAll 服务端静默失败，造成前后端永久分叉 【P0｜工作量：小】
- **证据**：`adminClearAll`（L4022-4050）中 L4030-4036 对 Supabase 发起 fire-and-forget 删除，**不 await、不检查错误**；而 `supabase-rls-修复v2.sql` 中 punches 表有不可变触发器、config 表禁止 delete——这些删除在服务端必然失败。
- **问题**：管理员点"清空"后本地干净了，服务端数据仍在；下次 Realtime/轮询同步会把"已清空"的数据又拉回来，或者不同设备看到完全不同的数据；这是数据一致性事故而非功能。
- **建议**：① 立即给这些删除调用加 `.then/.catch` 并把失败明确提示给用户（小）；② 若确实需要清空能力，实现带二次确认的服务端 RPC（中）；③ 若不需要，直接移除该按钮。

### B-6 回归测试套件当前失败 【P1｜工作量：中】
- **证据**：`test_outputs/run_regression6.log` 显示 `test_scripts/test_v20260806_regression.py` 第 99 行 `login_admin` 抛 Playwright TimeoutError；`test_outputs/` 中大量 `99_*_error.png`、`12z_error.png` 失败截图。
- **问题**：最新版本（v2026.08.05.15 之后的回归）在管理员登录环节就跑不过去，意味着当前线上版本的核心管理流程**没有有效的自动化质量门禁**，与"68 项安全测试全部通过"的历史报告状态不符。
- **建议**：先定位 login_admin 超时根因（选择器变更 or 登录流程改动 or 环境）；修复后将回归测试纳入每次发版前的强制步骤（配合 B-2 的 git + CI）。

### B-7 性能热点 【P2｜工作量：中】
- **证据**：① 364KB 单文件首屏全量加载（无代码分割、无压缩策略，仅靠 CF Pages 缓存规则）；② `syncToFB` 全量 upsert 随数据量线性增长；③ `initFBListeners` 中 Realtime 与自适应轮询双通道并存，重复渲染；④ 月度绩效 `calcMonthMetrics` 每次渲染遍历全部 picks/punches。
- **建议**：拆分后做按需加载（大）；全量 upsert 改增量（随 B-3 一起）；轮询与 Realtime 二选一、事件去抖（小）；绩效计算结果按月缓存（小）。

### B-8 错误处理与安全日志可观测性不足 【P2｜工作量：小】
- **证据**：多处 Supabase 调用以 `console.warn` 吞错（如 `syncToFB`、`adminClearAll`）；`logSecurityEvent`（L682 附近）记录 `ip:'client'` —— 纯前端拿不到真实 IP，安全事件日志在仲裁/溯源时证明力弱。
- **建议**：统一错误上报通道（写入 logs 表，该表已有不可变触发器保护）；真实 IP 改由 Supabase Edge Function / 数据库触发器从请求头获取（中）。

## C. 风险专家视角

### C-1 管理员认证完全在客户端，任何用户可伪造管理员 【P0｜工作量：中】
- **证据**：管理员密码哈希存于浏览器 localStorage `ca6pwd`（L3953-3964，默认 `admin123`）；`doLogin`（L3996-4019）、`genAdminToken/verifyAdminToken`（安全模块内）全部在客户端完成；`isAdminNow` 对无 `.` 的旧 token 直接 `return true; // legacy token, still valid until expiry`（L757）。
- **现状核对**：《安全风险排查报告.md》已将此列为未解决的最高危项——**本次复查确认仍未解决**。攻击路径：DevTools 写入 `cs6`/`cs6tk`、或直接调 `isAdminNow` 依赖的本地状态，即可执行审批、清空、改配置等全部管理操作；Supabase 端没有"管理员身份"概念，RLS 无法区分管理员与普通成员。
- **建议**：管理员校验服务端化——Supabase 新建 `admin_verify` RPC（密码哈希存服务端 secret 或独立 admin 表 + RLS），返回短时效签名 session；所有管理写操作走仅服务端校验通过的 RPC。过渡期：立即修改默认密码并移除 L757 legacy 分支（小）。

### C-2 成员密码存在明文比较遗留分支 【P1｜工作量：小】
- **证据**：`confirmPwd`（L1669-1711）中 L1683：`matched=(stored===inputVal)||(!isHash(stored)&&stored==null&&inputVal==='123456')||(isHash(stored)&&stored===inputHash)` —— 中间分支允许"无存储值 + 输入 123456"直接通过，且第一个分支是明文全等比较的遗留路径。
- **建议**：删除明文比较与 `123456` 后门分支，只保留哈希比较；对存量明文存储的成员强制一次重置。

### C-3 密码哈希随全量同步对所有人暴露 【P0｜工作量：小】
- **证据**：`syncToFB`（L1169 附近）把整个 `TEAM` 数组（含每位成员的 `pwd` 哈希）upsert 到 config 表；config 表对匿名用户可读（Supabase publishable key 在前端公开，L543）。
- **现状核对**：《安全风险排查报告.md》已列为未解决高危——**复查确认仍存在**，且因全量 upsert 机制，每次排班变更都会把密码哈希重新广播一遍。
- **建议**：① 立即从 `syncToFB` 的写入载荷中剔除 `pwd` 字段（小，一行改动级别）；② config 表 RLS 收紧 + 清理历史行中的 pwd 数据（小）；③ 成员认证长期应与 C-1 一起服务端化。

### C-4 CSP 允许 unsafe-inline 与 unsafe-eval，XSS 纵深防御缺失 【P1｜工作量：中】
- **证据**：L6 meta CSP：`script-src 'self' 'unsafe-inline' 'unsafe-eval' ...`。sanitize/sanitizeText 存在且被使用（历史报告 12 项 XSS 修复属实），但 CSP 本身形同虚设——任何注入的内联脚本都可执行。
- **建议**：配合 B-1 拆分，把内联脚本迁出为独立文件后，CSP 收紧为 `script-src 'self'`，去掉 `unsafe-eval`；上线前用 Playwright 验证无 console CSP 报错。

### C-5 部署安全响应头缺失（文档宣称已修复，实际回归） 【P1｜工作量：小】
- **证据**：《安全风险排查报告.md》宣称已添加并验证 HSTS、X-Frame-Options、CSP 响应头、Permissions-Policy；但 `outputs/_headers`（122 字节）实际内容只有：
  ```
  /version.txt
    Cache-Control: no-cache, no-store, must-revalidate
  /index.html
    Cache-Control: no-cache, must-revalidate
  ```
  所有部署 zip 中携带的也是同一份残缺文件。**修复丢失/从未落地**。
- **风险**：点击劫持（无 X-Frame-Options/frame-ancestors）、降级攻击（无 HSTS）、第三方嵌入与传感器 API 滥用（无 Permissions-Policy）。
- **建议**：立即补齐 `_headers` 并部署后用 `curl -I` 验证；把 `_headers` 内容纳入回归测试断言，防止再次静默回归。

### C-6 设备绑定指纹可伪造 【P1｜工作量：中】
- **证据**：`devFp()` v2（L826-836）= 屏幕分辨率 + 时区 + CPU 核数 + colorDepth，存于 `cb6`。无 Canvas/WebGL 熵、无服务端绑定记录。
- **风险**：① 同型号手机大量碰撞，"设备绑定"实际区分度低；② 用 DevTools/自动化脚本可任意伪造指纹代打卡；③ 绑定关系存 localStorage，清缓存即"换设备"。
- **建议**：设备绑定记录上服务端（member_id ↔ fp_hash ↔ 首次绑定时间 ↔ 管理员确认状态）；指纹碰撞时走人工确认而非自动放行；明确告知员工设备绑定规则（合规要求）。

### C-7 合规风险：考勤数据的劳动仲裁证据链不完整 【P1｜工作量：中】
- **证据**：① 审批人硬编码 `'管理员'`（L2902/2911/3199/3207，见 A-2）；② 离线打卡用本地时钟（L1951-2021），本地时间可被篡改；③ 补录窗口宽达 7 天（`validatePunch` L761-775）；④ 安全日志无真实 IP（B-8）。**正向证据**：服务端 punches/logs 表有不可变触发器（`supabase-rls-修复v2.sql`，已验证）——但仅覆盖成功上链的数据。
- **风险**：员工主张加班费/否认迟到时，企业方证据需满足"生成时间可信、修改留痕、操作人可识别"；离线卡与审批记录目前不满足，仲裁中证明力弱。
- **建议**：① 所有打卡记录服务端存储"接收时间 + 客户端声明时间 + 来源（在线/离线/补卡）+ 操作人"；② 审批记录具名化；③ 数据保留策略：考勤数据至少保存 2 年（参照劳动争议时效与各地工资支付规定）。

### C-8 隐私与个人信息保护 【P2｜工作量：中】
- **证据**：成员姓名、密码哈希、设备指纹、打卡轨迹均存于 config/punches 表且经全量同步广播；无隐私政策、无数据导出/删除用户请求处理、无最小化采集设计。
- **风险**：《个人信息保护法》视角下，考勤轨迹属个人信息，向全体客户端广播密码哈希与全员数据超出必要范围。
- **建议**：随 C-3 收窄数据广播范围（每人只拉自己的 + 公开排班）；补隐私说明页；定义数据保留与删除流程。

### C-9 运营单点与数据备份缺失 【P1｜工作量：小】
- **证据**：① 管理员仅一个密码（`ca6pwd`），丢失/误清 localStorage 即无法恢复管理权限，无重置流程；② 无自动备份——历史数据只存在于 Supabase 单 project + 用户浏览器 localStorage；③ `adminClearAll` 可一键清本地（B-5）。
- **建议**：① Supabase 开启每日自动备份（PITR 或 pg_dump 定时任务，控制台配置级别，小）；② 管理员凭证恢复流程（通过 Supabase 控制台直接重置 admin 密码哈希）；③ `adminClearAll` 按 B-5 处理。

### C-10 业务风险小结
- 资损路径：伪造管理员（C-1）→ 审批虚假补卡/请假 → 绩效 `calcMonthMetrics` 自动计入 → 工资错发。该链条目前**无任何一环能拦截**。
- 争议路径：离线卡 + 7 天补录窗口 + 不具名审批（C-7）→ 仲裁举证困难。
- 建议把 C-1、C-3、C-5、B-5 视为同一优先批次（均为"已知、高危、修复成本不高"）。
